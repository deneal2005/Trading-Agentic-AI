# Platform audit — 2026-10-29

Scope: the whole `trader_ai` repository at commit `900a728` (branch `feature/ui-overhaul`, which contains PRs #3–#8 plus the UI overhaul), run on the owner's Windows PC with the real local database and the Alpaca **paper** account.
Method: discovery, static inspection, the existing test suite, purpose-built probes (`audit/audit_probes.py`, results in `audit/results_2026-10-29.json`), one read-only live data fetch, and secret scans. **No orders were placed (not even paper orders); no settings, balances or the real database were modified.** Broker behaviour was tested against mocks.

Status legend: **PASS** verified by a test · **FAIL** defect reproduced or confirmed in code · **BLOCKED** couldn't run · **NOT TESTED** out of reach this pass.

---

## 1. Executive summary

**Decision: NOT READY FOR LIVE TRADING.** Live trading is also impossible by design (code and config refuse it). Under the current settings (order submission off, no promoted strategy), the system can't place any order, so there is **no immediate financial risk**.

What is solid:
- The research method is honest: walk-forward testing, a single-use holdout, cost stress, baselines and a counted trial registry. Features and labels pass leakage tests.
- The risk engine rejects stale quotes, off-market prices, missing stops, oversized positions and anything while the kill switch is on. The kill switch survives restarts. Duplicate orders are blocked, and live accounts are refused.
- The local UI server can't be driven by other websites (Host, token and origin checks; tested). No secrets are in git history, logs or the database.

What must be fixed **before order submission is switched on, even for paper**:

| ID | Severity | Problem in one line |
|---|---|---|
| F-01 | P1 | A strategy counts as "approved to trade" if it passed on **any** market and settings, not the ones it will trade |
| F-02 | P1 | The single-use holdout result isn't required before trading |
| F-03 | P1 | Today's **unfinished** daily candle is stored and used for decisions (confirmed with live Yahoo data) |
| F-04 | P1 | The "pause after N losing trades" limit can never trigger: nothing counts losses |
| F-05 | P1 | Daily-loss and drawdown limits only run when a *new* order is proposed, from a baseline recorded late in the day |
| F-06 | P1 | The no-trade window around big announcements silently switches off when the calendar is empty. It is empty right now: 0 events |

Model and strategy validity: **no strategy or model has shown a tradable edge** (E6–E18). The two research trend rules (E13, E15) matched buy-and-hold's Sharpe with half the drawdown, but the gate rejected them, and over-fitting is visible in the per-fold results (§6). There is nothing to deploy yet, which is a correct outcome, not a defect.

## 2. Architecture and data flow (verified)

```
Yahoo / Stooq / Alpaca bars ──► validate_bars ──► SQLite `bars` (one row per day, INSERT OR REPLACE)
Forex Factory + central-bank RSS ──► NewsStore (events, news, source_health)
                                         │
tradeintel run-once / service ──► run_cycle (file lock: one cycle at a time)
   ├─ BarStore.load ─► strategy.signals (closed bars) ─► agents (market, news, quant, adversarial)
   ├─ coordinator ─► Decision (logged to `decisions`)            ← quant agent receives no model (not wired)
   ├─ if enter/exit: StateStore day/hwm ─► sizing (risk_per_trade / stop distance)
   └─ ExecutionPipeline: broker.account/quote/positions ─► RiskEngine.evaluate ─► broker.submit_market ─► `audit`
Brokers: PaperBroker (SQLite), AlpacaPaperBroker (paper host only, "PA" accounts), OandaPracticeBroker (practice host only)
Research: research() walk-forward + cost stress + baselines + gate ─► Registry `experiments`; holdout_test() single use
Model: make_features ─► walk_forward_eval (logit | MLP) ─► ModelRegistry (pickle + meta); used only by the UI brain view
UI: stdlib HTTP server on 127.0.0.1 ─► read models + actions that call the same backend functions
```

Stack: Python 3.14, pandas, scikit-learn, SQLite (WAL), requests. Front end is build-free ES modules with vendored Lightweight Charts and three.js. About 5,300 Python lines and 1,950 JS lines; 13 test files.
Market: **SPY daily** (equity, USD), with EURUSD daily data also stored. Timeframe: daily swing/position. No intraday logic.
Scheduling: `tradeintel service` (a sleep loop, run manually). No OS scheduler or heartbeat.

## 6. Strategy and backtest credibility

Verified by reading the engine (`backtest/engine.py`) and its tests:
- Signals use closed bars; fills happen at the next bar's open plus half-spread plus slippage. Stops fill intrabar, or at the open if the price gapped through. If stop and target are both hit in one bar, the stop is taken (conservative). Financing is charged daily. Units are capped by leverage and max units. Each walk-forward fold starts flat.
- Sharpe is mean/std of daily equity returns × √252 with **no risk-free rate** (P3; document it). A bootstrap 90% CI is reported.
- Costs are realistic for SPY (2¢ + 2¢ per side). Short-borrow fees aren't modelled, which flatters short trades slightly. Cash earns 0% when flat, which slightly understates the trend filters.

Over-fitting evidence (from stored fold records):

| Exp | Strategy | Market | Folds | Best-parameter changes | Mean in-sample Sharpe | OOS Sharpe | Losing OOS folds |
|---|---|---|---|---|---|---|---|
| 4 | sma_cross | SPY | 18 | 13 of 17 | 0.59 | 0.18 | 11/18 |
| 5 | donchian_breakout | SPY | 18 | 12 of 17 | 0.23 | −0.01 | 10/18 |
| 6 | rsi_mean_reversion | SPY | 18 | 11 of 17 | 0.51 | −0.53 | 13/18 |

The optimiser's choice changes at almost every fold, and in-sample Sharpe doesn't carry forward. Trials per strategy reach 896 (sma_cross), and there is no deflated-Sharpe correction (P2). The gate rejected all of these, which is the correct outcome. Parameter-neighbourhood sensitivity maps don't exist (P2).

## 15. Regulatory and compliance questions (needs a qualified adviser)

Not legal advice; these are questions to ask, not conclusions.
- **Where you live.** The UI clock suggests an Indian time zone. If you are an Indian resident: overseas trading through a US broker falls under RBI's Liberalised Remittance Scheme and FEMA rules. Tax reporting of foreign assets and gains applies. Check Alpaca's eligibility for your country.
- **Personal use only.** If this is ever used for other people (signals, managed accounts, a paid product), investment-adviser or research-analyst registration may apply (for example SEBI in India, SEC/FINRA in the US), plus rules on performance claims. Backtests must never be presented as returns.
- **Data licences.** The Yahoo chart endpoint is unofficial and for personal use; check the Alpaca market-data terms and the Forex Factory export terms before any redistribution.
- **Automated execution.** Broker terms for algorithmic and API trading; record-keeping (the audit table is a start).

## Final readiness decision

**NOT READY FOR LIVE TRADING.**
It is suitable today for **research and observation** (order submission off), which is how it is configured. Before switching on **paper** orders, fix F-01 to F-06 and run a supervised paper-order lifecycle test (§14). Live trading would additionally need a strategy that passes the gate *and* the holdout, months of reconciled paper results, F-07 to F-12, and a separate, explicit decision. A passing software audit doesn't make a strategy profitable.
